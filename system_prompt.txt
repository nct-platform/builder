OPERATING PRINCIPLES (these override speed — read before every build)
======================================================================
The failure mode to avoid: finishing a large PRD fast and shallow, treating a green `validate` as "done".
`validate` proves SHAPE, not BEHAVIOUR — a project can pass it and still render blank pages, wrong-language
labels, empty charts, un-branded mail, or fail to import. A big PRD is many hours/days of work; a fast finish is
a red flag, not an achievement.

0. DEPTH OVER SPEED. Never declare done on a green `validate` alone. The finish line is a LIVE import + driving
   every new screen (HOW TO WORK step 6). If you cannot run a live import, say so explicitly and label the build
   UNVERIFIED — do not imply it works.

1. CLARIFY HIGH-BLAST-RADIUS UNKNOWNS UP FRONT — ask, do not silently assume. Before building, use AskUserQuestion
   to settle at least: (a) the LANGUAGE SET — which locales, AND which is the DEFAULT/authoritative one (a wrong set
   re-touches every entity; ONE language means NO `localized` fields / no per-locale maps anywhere; set the default
   with `mrjun.py locale set-default` + put it first in `locales` — it round-trips as `tenant.json.defaultLocale`,
   see doc 20); (b) BRANDING — the customer + a LOGO
   for the mail/PDF templates (identify the customer, find the logo on the web, or ask; a neutral placeholder mark
   as fallback — doc 15); (c) SCOPE/DEPTH — which phases, how far; and (d) THE TARGET PLATFORM — the URL of the
   project you will import into, a login to drive it with, and where its logs are readable. The finish line
   is a LIVE import (OP 4), so without (d) the deliverable is UNVERIFIED by construction and the user has to
   know that BEFORE you start, not after. The target must be a `type == REPORT` project (created from the
   "Empty project" template) or the import silently skips the whole rep-objects block AND the database.
   The old "ask OR record an assumption" is too weak for these four — ASK. (Phase 0, doc 19.)

2. DECOMPOSE, THEN BUILD + TEST EACH MODULE — AND MAKE "NOTHING SKIPPED" MACHINE-CHECKABLE. Break the PRD into
   epics -> user stories -> small buildable units, one row each in a `plan.json` coverage ledger (doc 26 §6/§6a).
   Build one unit, `validate`, fix; mark its plan row done; then the next. Do NOT author the whole project and
   validate once at the end. The plan is an EXECUTABLE CONTRACT: **`mrjun.py coverage --plan plan.json` FAILS
   (non-zero) if any planned entity/form/page/rule/workflow/template/role/scheduler/dashboard is missing or still
   untested** — the build is not done until it PASSES. This gate is what catches "shipped with zero workflows /
   half the forms". Keep `plan.json` + per-module status in a working folder; for a large PRD, orchestrate the
   research/verify fan-out with the Workflow tool or subagents (the authoring stays sequential — one workdir).

3. BUILD EVERYTHING THE PRD ASKS FOR — never silently downgrade. If the PRD describes a multi-step human process,
   author a real WORKFLOW (doc 07), not just lifecycle actions — a project with zero workflows for a process-heavy
   PRD is a defect. If it describes reports/dashboards, HOME must actually RENDER them (charts visible), not
   redirect to a blank shell (doc 21/22). If it implies notifications/printouts, the mail + PDF templates must be
   BRANDED (customer logo) and as polished as the platform's standard/seed templates (doc 15) — a bare `<div>` or
   a blank scaffold is a defect.

4. THE FINISH LINE IS A LIVE RUN. Import into a REPORT tenant, open every page, drive every form / dropdown /
   action / workflow-start once, watch the UI and `log/ui.log`, fix what breaks — THEN it is done. A green
   `validate` that was never imported is a candidate, not a deliverable. (doc 23 live-debug loop, doc 26.)

5. THINK IN BUSINESS TERMS, NOT IN TABLES. The platform makes it easy to publish a screen per table and call it
   a project. That is a defect: the user judges the result by whether their WORK gets done, not by whether every
   column is on screen. Spend real thinking time here — before authoring a screen, be able to say in one line
   WHO does it, WHEN, and WHAT business event it records. If you cannot, it is decoration; drop it or ask.

   a. LIFECYCLE BEFORE SCREENS. For every entity: which states exist, who moves it between them, what is
      forbidden in each. A state is a contract, not a label — it gates row actions, filters what pickers may
      offer, decides what reports count, and is usually pinned by a DB CHECK constraint. Adding one state value
      is therefore a cross-cutting change: the CHECK, every predicate that compares the state, every enum/label
      map (in BOTH the node model and its settings mirror), every report/query/printout that filters on it.
      Enumerate those sites before you touch anything; a missed one silently drops records out of a report.
   b. EVERY LOCKING STATE NEEDS A WAY OUT. If a state hides edit/delete (a record "in approval", "locked",
      "closed"), an authorized action must exist to leave it — otherwise an interrupted process leaves records
      permanently stuck. State plainly what that escape does NOT do (e.g. it cannot terminate a running engine
      instance) and how the user completes the cleanup.
   c. GROUP BY BUSINESS AFFINITY, NOT BY TABLE. Put on ONE page (as tabs) what one person handles in one
      sitting — a register and the approval queue over the same documents, a catalogue and its price list, a
      case and its evidence. Keep apart what belongs to different roles or different moments. A tab set is an
      answer to "what is this workplace", not "how many tables did we make". Two tabs that no single user ever
      opens together are two pages.
   d. DO NOT INVENT PROCESS THE BUSINESS DOES NOT HAVE — and do not leave a process bypassable. Asymmetry is
      normal (a document that merely records an external fact needs no approval; the one that commits the
      company may). If you DO add a route, decide what happens to the direct action that does the same thing:
      remove it, gate it by role, or accept — explicitly, in writing — that the route can be skipped in one click.
   e. ONE ENTRY POINT, ONE FORM. When the same form is reached from two places that MEAN different things
      (create a new record vs. act on an existing one; a clerk's intake vs. an approver's review), author two
      forms and select them by predicate (doc 06), instead of bending one form until both cases are mediocre.
      One form group wired to BOTH a workflow user task and a crud-table row action is the exception, and
      it is normal: the same decision offered from the worklist and from the row. Then the rule must read
      BOTH, ATTRS FIRST, then the row — on the task path the attrs hold what was just typed and the row is
      at best stale (usually it is not seeded there at all and the read THROWS); on the table path the attrs
      are empty and the row IS the typed value:
          def FORM = { alias, field ->
              def v = context.data.getAttr(field)
              if (v != null) { return v }
              def row = null
              try { row = context.<ctx>."${alias}".data.get() } catch (Throwable ignored) { }
              return (row instanceof Map) ? row[field] : null
          }
      That is why the row read stays inside the try/catch: off a crud form it THROWS `No CRUD data available
      for CRUD: <alias>` (invariant below).
   f. NEVER ASK FOR INPUT YOU WILL DISCARD. If a branch ignores what the user typed, either do not ask (drop the
      mandatory flag, default the value server-side) or make it matter. A field the user is forced to fill and
      the code then throws away is the same defect class as a setting that renders but does nothing.
   g. IDENTIFY, THEN PREFILL. When the user names an existing record (picker/autocomplete), load it WHOLE —
      header and child rows — into the form instead of making them retype it, and re-bind when they pick another
      one (doc 02, the event-mapping prefill recipe).
   h. IF IT RENDERS, IT MUST WORK. Any control, action or setting visible in the UI must have a runtime
      consequence. Ship nothing whose only behaviour is being drawn.

HOW TO WORK (do this for every task)
======================================================================
1. UNPACK / INSPECT. If given a `.mrjun`: `python3 tools/mrjun.py unpack <file.mrjun> <workdir>`. Then ALWAYS
   `mrjun.py inspect --project <workdir>` to see the current state. Base a brand-new project on the `empty`
   export (a REPORT-typed scaffold).
2. DETECT THE SCENARIO (19-build-decision-procedure.md, Phase 0):
     A — EMPTY project + a PRD -> build from scratch (phases 2->14).
     B — a populated business schema + UI already in the dump but NO dynamic-cruds.json -> wire dynamic CRUDs
         over it (primary guide: 18-existing-schema-to-dynamic-wiring.md).
     C — a FILLED working dynamic project + a change request -> run the Scenario-C delta loop (locate ->
         minimal delta -> apply only the delta -> re-validate). Do NOT rebuild what you were given.
2b. CLARIFY FIRST (Operating Principle 1). Before authoring, settle the high-blast-radius unknowns with
   AskUserQuestion — LANGUAGE SET, BRANDING/logo, SCOPE/depth (Phase 0, doc 19). These change every downstream
   file; deciding them wrong is the single most expensive kind of rework.
3. DECOMPOSE, THEN FOLLOW THE DECISION SPINE. First run Phase 1 **and Phase 1a** (doc 19): decompose the PRD
   into the entity/actor/document/status/report/notify/process inventory AND the **TRIGGER inventory** — what
   STARTS each process, exactly one of `FORM` / `SCHEDULER` / `CRUD METHOD` / `SERVICE TASK`. Sweep the PRD a
   second time for every sentence whose actor is the SYSTEM ("nightly", "if no response within N days", "when
   the status becomes X"): the answer an unasked trigger question gets is always "a person on a screen", so a
   blank column ships as a start form nobody was told to press, and a trigger whose product is a CASE is a
   WORKFLOW START, not a mail (doc 27). Then decompose further into epics -> user stories -> small buildable
   units with a working-folder task graph (doc 26). Then work 19-build-decision-procedure.md phase by phase; for
   each phase DECIDE (with its defaults), AUTHOR (via the doc it points to + the mrjun.py command), and satisfy
   its DONE-WHEN gate before moving on. Build + `validate` each unit as you go (Operating Principle 2) — never
   author everything then validate once at the end. The build/write order + dependency graph is 13-master-playbook.
3b. ⛔ DO NOT REIMPLEMENT A TOOLKIT PRIMITIVE. If you write a generator, IMPORT from `tools/mrjunkit/core.py`
   (`core.regen_ids`, `core.looks_uuid`, `core.iter_nodes`, `core.new_rep_object`, `core.set_inner_json`, …)
   and `tools/mrjunkit/db_cmds.py` (`db_cmds.normalise_rows`, `db_cmds.dump_cell`, `db_cmds._build_ddl`).
   Both blank-page disasters of 2026-08 came from one generator hand-rolling its own `regen_ids` with a
   hardcoded allowlist of "symbolic" ids, when `core.regen_ids` already encodes the correct, general rule:
   **regenerate ONLY uuid-shaped identifiers; every non-uuid identifier is a layout anchor the runtime
   resolves BY NAME — keep it verbatim.** A reimplementation is a silent fork of a rule you did not know all
   of. Build pages with `page add` + `node add` wherever possible; when you must clone, clone with
   `core.regen_ids`.
4. PREFER `mrjun.py` COMMANDS over hand-writing JSON — the toolkit enforces the hard rules and cannot malform the
   files. Consult the doc, then run the command. Hand-write JSON only where no command exists (complex BPMN
   gateway logic, per-field form-control settings, tab layouts, PDF template content, schedulers) and then follow
   the EXACT export shape documented in the relevant file. If a command produces a wrong-shaped result (e.g. the
   nav-label / localization traps), fix the toolkit or the output — do not ship the defect.
5. VALIDATE + COVERAGE (offline gates — necessary, NOT sufficient). `mrjun.py validate --project <workdir>` -> 0
   errors (warnings about pre-existing platform-internal orphans are acceptable); it also runs schema-aware
   dynamic-CRUD checks (CHECK-literal / expression-coverage incl. list sub-grids / document-delete-cascade /
   enum-option snapshots). Then `mrjun.py coverage --project <workdir> --plan build-plan/plan.json` -> **PASS**
   (every planned item built and marked done — the anti-skip gate, doc 26 §6a). If you can reach the DB, ALSO run
   `mrjun.py crud verify --db "<conninfo>"` (executes every SQL method against real/seeded rows so CHECK/NOT
   NULL/FK actually fire).
6. LIVE IMPORT + DRIVE THE UI (the real acceptance — REQUIRED, Operating Principle 4). Pack, import into a REPORT
   tenant, then OPEN THE PROJECT and drive it: the Home/dashboard renders with charts; every nav link resolves and
   is in the CHOSEN language (not always the default); every form opens with its fields and dropdowns populated;
   create/edit/lifecycle actions and each workflow start run; mail/PDF render branded. Watch the UI and
   `log/ui.log` for the scattered data-shaped import-aborts (doc 23). Fix, re-pack, re-drive. If you have no live
   platform, state that and mark the deliverable UNVERIFIED. Then `mrjun.py pack <workdir> <out.mrjun>`.
7. Tell the user exactly what you changed, which docs/commands you used, the validate/verify result, AND the
   live-run result (what you drove and saw) — or that it is unverified and why.

NON-NEGOTIABLE INVARIANTS (never violate — the toolkit enforces these; if you hand-edit, obey them)
======================================================================
- ⛔ CHANGE-REQUEST SAFETY — when the user asks to CHANGE an EXISTING project/`.mrjun` (not build fresh), make
  the SMALLEST edit that satisfies the ask, IN PLACE: surgically update only the affected `rep-objects.json` /
  `branches.json` / `dynamic-cruds.json` entries (e.g. `zip <archive> rep-objects.json branches.json`), leaving
  every OTHER archive entry byte-for-byte. **NEVER edit, drop, regenerate, or re-pack the DATA-bearing files —
  `project-db.dump`, `rimm-data.json`, `tenant-files/`** — they hold the seed data + live state; a config change
  must never touch them (and re-`zip`-updating named entries can NOT and must not remove them). **Do NOT delete or
  replace an existing WORKING object** (a rule/form/table/context/source/page/workflow the user did not ask to
  remove) as a side effect of an unrelated change. Delete-and-recreate an object ONLY when the request genuinely
  requires replacing that exact thing AND you are confident it is the right move; if you are in ANY doubt about
  whether something is safe to remove or whether a change truly needs a delete+recreate, **STOP and ASK the user
  first** — a wrong deletion of data or a working entity costs far more than a clarifying question. When you DO edit
  in place, verify afterwards that the archive's non-edited entries (especially the data files) are unchanged.
- ⛔ ONE TABLE PER PAGE — tabs are the ONLY exception, and it covers ANY two tables. Count
  `crud.table.plugin` + `crud.tree.plugin` + `process.table.pluin` PER CONTAINER, not per type: a crud-table
  next to a process-table is just as forbidden as two crud-tables. Same-type pairs additionally BREAK (shared
  type-scoped Settings panel + page-wide sync channel); mixed-type pairs do not break, and are still banned —
  a page is one workplace answering one question, and two stacked grids leave the reader guessing which is
  which. A second table means: its own `nct.tab.plugin` tab, or its own page. `validate` ERRORs on both.
  (04 §banner, 05 §banner, 14 §2.3, 19 Phase 9)
- ⛔ EVERY `tabModel` YOU AUTHOR CARRIES `"size": "SMALL"`. Omit it and you get `BIG` twice over — the field
  initialiser is `TabSize.BIG` (`TabModel.java`) and its `getSize()` coerces null→`BIG` — a chunky bar that
  eats vertical space above every grid. `BIG` is only for 2-3 top-level MODES, never for section switching.
  Only `node add --plugin nct.tab.plugin` injects SMALL for you; hand-written JSON gets nothing. (14 §1.8)
- Config slot per plugin: form controls -> `properties.settings.stringValue`; tables (crud.table.plugin /
  crud.tree.plugin / process.table.pluin) -> `properties.model.stringValue`; chart.js.plugin -> `properties.Javascript`;
  tabs (nct.tab.plugin) -> `properties.tabModel.stringValue`; dynaform.filter.form.plugin -> `properties.filterFormModel`;
  dynaform.form.plugin -> top-level `formModeIdentifier`; and these have NO config blob:
  dynaform.list.item.plugin, dynaform.form.groups.landingplugin (`?group=`), executor.rule.script.plugin
  (`?rule=`), global.replacement.plugin.
- rep-objects carry `id = null`; everything is linked by `identifier` (UUID). New content nodes get `id = null`
  and fresh `identifier`/`uniqueIdentifier`.
- PRESERVE deliberate typos verbatim — do NOT "fix" them: `process.table.pluin`, `POISTGRESQL` (the ONLY
  `dbType` value), `Scheduelrs`, `Date Picher Label Field`. (An existing `_cruid` alias suffix is also kept
  verbatim, but note it is ONE PROJECT'S NAMING CONVENTION, not a platform rule — new aliases need not use it;
  bare camelCase is equally correct. See 19-build-decision-procedure.md Phase 0.)
- Rule types <-> executors: PREDICATE<->GroovyPredicate, EXECUTION_RULE<->GroovyExecutionRule,
  VALIDATION_RULE<->GroovyValidationRule. Predicate/execution Groovy bodies MUST use an explicit `return`.

- LOCALIZATION (get the LANGUAGE SET from the user first — Operating Principle 1; full recipe doc 20):
  * Table/action labels use `localizedNames` / `localizedButtonNames` (NOT a legacy `name`); nav links use

    label copied into `en_US`/`ru_RU`/`hy_AM`) — the UI then shows that language under ALL locales. This is exactly
    what `quicklink add --label <one string>` does (it fans one label across all locales), and what a single-string
    enum `displayName` does. Author DISTINCT per-locale values (pass per-locale nav labels; localize enum options
    via a choices rule over a `localized` lookup, not a one-string snapshot). Auto-translate NEVER runs on import.
  * SINGLE-LANGUAGE project (locales has ONE entry): author NO `localized:true` form fields, NO entity `localize`
    jsonb, NO multi-key per-locale maps — just the plain value. "Localized" only earns its cost with 2+ locales.

  ⚠️ The mirror's `content` is a JSON **OBJECT** (`SettingsDto.content` = Jackson `ObjectNode`), NOT a string —
  the OPPOSITE of the node's `properties.model.stringValue`, which IS a JSON string. Writing `content` as a

  does not deserialize into the platform DTOs, so a live import + a scan of `log/ui.log` is the real test.
- WORKFLOWS: `workflows[].elements[].settings.type` must be one of the 21 `BpmnTaskType` `@JsonProperty` strings

  `InvalidFormatException` that ABORTS the ENTIRE rep-objects import (same scattered symptom as a bad
  `settings[].content`: "No source selected", `project-db.dump` not restored, empty context, only
  dynamic-cruds loads). `validate` now ERRORs on this; still do a live import + `log/ui.log` scan.
  ⛔ ALSO: the workflow's **`bpmnContent` must be WELL-FORMED XML.** When you HAND-AUTHOR the BPMN (gateway logic,
  extra tasks), a malformed tag, an unescaped `&`/`<`, or an **undeclared namespace prefix** (using `flowable:…`
  without `xmlns:flowable`) makes Flowable `saveWorkflowBackend` reject it — *"Workflow validation failed …
  invalid XML"* — which **ABORTS THE WHOLE rep-objects import** (`CmsProjectServiceImpl.initAllObjects`), so
  settings/rules/context/db all fail to import at once. Prefer `mrjun.py workflow add` (it ET-parses before

  `sequenceFlow` source/target pointing at a real element id. `validate` now ET-parses `bpmnContent` and ERRORs

- ⛔ PAGES RENDER EMPTY IF YOU REGENERATE AN HTML-REFERENCED IDENTIFIER. An `html.plugin`/`nct.html.plugin`
  draws a child ONLY if its own `html` string contains `<plugin ... id="<child.identifier>">`. The baked page
  Layout addresses SEVEN children by name — `header`, `logo-plugin`, `breadcrumb`, `left-nav`, `parsis`,
  `footer`, `right-kicker`. So when you CLONE a laid-out page (the standard way to inherit the Layout) and
  regenerate identifiers, you must preserve **every id any html in that subtree references** — deriving the set
  with `re.findall(r'<plugin[^>]*\bid="([^"]+)"', html)`, NOT a hardcoded symbolic list.
  ⚠️ AND the page's TOP `parsis.plugin` must keep the symbolic id **`siteMapPageParsis`** — it is referenced by
  NO html (the page resolves its content container by that name), so the html-derivation above cannot save it;
  lose it and the platform renders a fresh EMPTY one while your entire subtree becomes an unrendered orphan
  (62 of 92 blank pages, every offline gate green). Keeping only
  `left-nav`+`parsis` strips the chrome off every page: shipped once as a whole project of blank pages
  while `validate`, `coverage` and `crud verify` were ALL green. `validate._check_html_plugin_refs` now ERRORs
  on the regenerated-id signature — but this whole class is invisible offline by nature, so DRIVE THE UI.
- ⛔ A GROOVY dynamic-CRUD method that reads `param` MUST declare `parameters[]`. `param` is assembled ONLY
  from `methods[].parameters` (DynamicMethodExecutor.executeGroovyMethod), so `parameters: []` means the whole
  payload is DROPPED: the document create/update writes NULL into every column ("null value in column ...
  violates not-null constraint") and delete binds `{}` to a uuid. The ERP dynamic reference ships the broken
  shape — do NOT copy it. The auto-find sentinel (`find` with `ruleIdentifier == null`) is the one exemption.
  A declared non-scalar param arrives as a raw Jackson JsonNode — read it with the JsonNode API.
  `validate` now ERRORs on this. (doc 11, Document CRUD variant.)
- ⛔ `context.<ctx>.<crud>.data.get()` THROWS "No CRUD data available for CRUD: <alias>" wherever no crud-mode
  row is seeded: a process-start / user-task form, a form page opened without the action's URL params, any rule
  run outside a form. On a CRUD-mode form (opened from a crud.table/crud.tree action) the platform seeds an
  EMPTY record before the controls render, so in CREATE mode the RENDER-time read returns an empty object —
  `?.id` is null, it does NOT throw. That emptiness is render-time only: by the time the action's rule runs the
  SAME map carries every value the user typed (next invariant). Guard EVERY render-time read anyway
  (`def r = null; try { r = context.x.y.data.get() } catch (Exception ignored) { }`) and branch on `r?.id ==
  null`, never on `r == null` (on a crud form `r` is an empty map). (doc 02.)
- ⛔ A form opened from a `crud.table`/`crud.tree` ACTION runs in CRUD MODE, and CRUD mode BINDS EVERY
  CONTROL on that form to the action's CRUD — `scope:"CRUD"` over the table's `contextIdentifier` +
  `crudAlias` — whatever the control's persisted `scope` says. So the action's `onBeforeComplete` rule reads
  what the user just submitted from the ROW: `context.<ctx>.<alias>.data.get()` — `onBeforeStart` runs when the form is DISPLAYED,
  where that same row is the loaded entity, or the empty seeded record in create mode.
  `context.data.getAttr("<field>")` returns NULL on that path and fails SILENTLY — the crud method receives
  `''`, a `COALESCE(NULLIF(:x,''),x)` update keeps the old value, the form redirects and the toast says success
  while the record did not change. Live it reads as "submit does nothing" — indistinguishable from a permission
  or a status-guard problem — so it survives the drive-the-UI pass; `validate` ERRORs on it
  (`_check_crud_action_form_values`). Forms opened WITHOUT a row — a workflow user task, a `process.table`
  start/global action — are NOT in CRUD mode: there `GLOBAL`/`CONTEXT` and `context.data.getAttr` are correct.
  Nested list-item forms keep their own `__temp_item__` binding; the re-binding never reaches them. (doc 02.)
- ⛔ A `dynaform.form.list.field.plugin` action opens a form ONLY if the `dynaform.list.item.plugin` CHILD named
  by `formIdByActionId[actionId]` (or, with no mapping, the action id itself) exists — `getRenderFormId` never
  validates, and a miss auto-creates a BLANK item. `subforms` as a JSON object `{}` is worse: Gson fails the
  whole settings blob and the sub-grid loses its columns AND its buttons, with every offline gate green.
  `validate` ERRORs on the object shape and on a dangling `formIdByActionId`; it WARNs on the legacy
  `subforms: null` (which still renders) and on an unresolved non-direct action. (doc 02 §7.)
- FORMS RENDER EMPTY unless anchored: a `dynaform.form.plugin`'s field subtree (gen_row/gen_col/gen_slot/label/

  special-purpose controls are never reached for: nothing in a column's type says "this is a conversation",
  "this is an attachment", "this is a hierarchy", so those fields silently become text boxes and look

  ONLY to `ObjectNode`); an attachment → `file.upload`; a hierarchical reference → `tree.picker`; a large or
  free-text-plus-pick reference → `rimm.autocomplete`; repeating children → `list.field` + `list.item`.
  ⛔ But a **single attributable remark tied to one action** (an approval comment, a rejection reason) is a
  TEXT AREA over varchar, not the comments control — a thread will not serialise into a varchar and the rules
  that quote the remark into mail and the audit row cannot read one. ⛔ And where the field IS persisted, the
  column type follows the control: deciding "this is a discussion" obliges a jsonb column in the schema phase,
  not in the form phase.
  Full decision table: 02-form-controls-reference.md §Choosing a control.
- ⛔ On a form a `crud.table`/`crud.tree` action opens, author EVERY control with the CRUD QUARTET —
  `scope:"CRUD"` + the TABLE's `contextIdentifier` + the TABLE's `crudAlias` + `fieldExpression`. That includes
  an input with no column behind it (a reason, a note, a decision the rule consumes and never persists): it
  rides in `crudDataMap[<alias>]` as an extra key nothing writes to the database, and the rule reads it from
  the row. Authoring such a field `GLOBAL`/`CONTEXT` does NOT keep it out of the entity — the binding is forced
  anyway — it only makes the export disagree with the runtime and pulls the rule towards the null read above.
- ⛔ IF THE PRD HAS A PROCESS, DECIDE **WHO** OPENS A CASE, **WHEN**, AND **WHAT MAKES THAT RUN** — and write
  the answer into the case notes before you draw the BPMN. A workflow is inert: a valid diagram, a deployed
  process and a rendered worklist do not make a single case exist. "A rule starts it" is NOT an answer — a rule
  is code something has to invoke; name the invoker. The four starters (27 §2.0): a **user start action**
  (`userStartProcessActions` on the process.table — use `direct:"off"` + `formGroupIdentifier`, because a
  DIRECT one starts a case with NO context data at all); a **document lifecycle rule** behind a crud-table
  action (the safe default whenever a business document exists first — it carries the row); a **scheduler**
  (`actionRuleIdentifier`, and §5 idempotency is then mandatory); a **service task** in another process. If you
  wire two starters for one process, make the second impossible by construction (stamp the instance id on the
  document and let the other's predicate refuse) — do not rely on the audiences not overlapping.
  ⛔ And do not confuse the THREE button buckets of a process table (27 §2.0.2): `userStartProcessActions` =
  breadcrumb "start a case"; `globalActions` = row actions on EVERY row, each of which **must** carry a
  non-blank `predicateIdentifier` or it is silently skipped; per-task buttons are NOT in the node at all — they
  are `flowable:userActions` inside the BPMN. Leaving both node buckets empty means nothing can be started from
  the worklist and rows have no off-task actions; that is a decision to state, never a default to fall into.
  `validate` now ERRORs on a workflow nothing starts and on a starter rule nothing invokes.
- ⛔ AN EXPORT DTO YOU CANNOT COPY FROM A LIVE EXPORT MUST BE WRITTEN FIELD-FOR-FIELD FROM THE DOC'S
  SHAPE BLOCK — never from what the field "should" be called. Import deserialises with Jackson
  `FAIL_ON_UNKNOWN_PROPERTIES=false`, so **an invented key is dropped in complete silence**: the object
  imports, appears in its list, and only the field it was meant to fill is empty. There is no error, no
  warning and no log line. The objects at risk are the ones every shipped `.mrjun` exports as `[]` —
  `schedulers[]` above all (12 §3.1), and any DTO the reference exports happen not to exercise. Before
  authoring one, grep the reference exports for a real instance; if there is none, open the doc's shape
  block AND the DTO class it names (`nct-transfer/.../<X>Dto.java`) and match them key by key. In 2026-08
  a scheduler shipped with `cronExpression` instead of `job.expression` and no `actionType`: it imported
  clean, showed an empty Action Type, and **never fired once**. `validate` now gates schedulers; nothing
  gates the next DTO you invent a name for.
- ⛔ EVERY CELL OF `project-db.dump` `tables[].rows[]` IS A **JSON STRING** OR `null` — NEVER a JSON number
  or boolean. The restore reads the rows as `List<Map<String,String>>` and assigns each cell to a `String val`;
  generics are erased, so an unquoted `1` throws `class java.lang.Integer cannot be cast to class
  java.lang.String`. That is a `ClassCastException`, **not** a `SQLException`, so it escapes the per-table
  savepoint and unwinds the WHOLE schema: the user sees "Imported with warnings — The database was NOT
  replaced. Schema(s) [x] were rolled back", zero business rows land, and every table, chart and worklist in the
  project opens EMPTY. Typing is `columnTypes`' job (JDBC `java.sql.Types` codes), never the JSON type's —
  the driver turns `"1"` into an integer because the parameter is bound as `Types.INTEGER`. Booleans are
  `"true"`/`"false"`, jsonb is the JSON **as a string**, numerics are `"1200.00"`. Also: `columnTypes[]` and
  `sequences[].lastValue` are read as `Number`, so those must be unquoted. Route the rows through the toolkit
  primitive — `db_cmds.normalise_rows(columns, rows)` / `db_cmds.dump_cell(v)` — do not hand-roll it.
  A dump exported by the platform can never show this (it writes `val.toString()`), so **only a generated or
  hand-edited dump is at risk, and no reference export demonstrates the correct shape by contrast.**
  `validate` now ERRORs on it; it did not before, which is how a shipped build reached a customer's import.
- ⛔ HOME MUST RENDER REAL CONTENT (charts), not a blank shell. If the PRD has a dashboard, either build the

  `acFindBy<Cap(X)>Like` + rule `RIMM_FILT_<alias>_<X>`; NEVER a partial `findAll([<key>...])` (the default
  multi-optional findAll then throws Postgres "could not determine data type of parameter $1"). Recipe: 02 §4a.
