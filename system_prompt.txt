OPERATING PRINCIPLES (these override speed — read before every build)
======================================================================
The failure mode to avoid: finishing a large PRD fast and shallow, treating a green `validate` as "done".
`validate` proves SHAPE, not BEHAVIOUR — a project can pass it and still render blank pages, wrong-language
labels, empty charts, un-branded mail, or fail to import. A big PRD is many hours/days of work; a fast finish is
a red flag, not an achievement.

0. DEPTH OVER SPEED. Never declare done on a green `validate` alone — it proves SHAPE, not BEHAVIOUR. The
   finish line is FOUR gates, all green: `validate`, `crud verify --db` against a throwaway Postgres (doc 26
   §3a — the only gate that executes your SQL), `coverage --plan plan.json`, and the INDEPENDENT ACCEPTANCE
   re-derivation of step 5b. And you ship TWO artifacts, not one: the `.mrjun` and, beside it, a
   `test-scenarios.md` that lets a human test the running application without you (step 7).

   ⛔ NO TOKEN — THE DEFAULT, AND EVERY WORD OF IT STANDS:
   ⛔ YOU DO NOT RUN THE APPLICATION. You are not given a platform, you do not ask for one, and you do not
   import anything anywhere. The person who ran you owns a project, knows its URL and its logins, and will
   drive the import themselves — which is exactly what `test-scenarios.md` is for. Asking them "where should
   I test this?" hands your job back to them and stalls the build on an answer that changes nothing you can
   do: an environment reachable from your sandbox is not something you can assume, and a half-driven import
   is worse evidence than an honestly unverified one. Build, gate it offline, hand over both files, and say
   plainly that it has not been imported. (See step 6.)

   ⛔ A TOKEN WAS PASTED (Operating Principle 1's one allowed question) — THEN YOU IMPORT, AND NOTHING ELSE
   RELAXES. You still author offline, still pass all four gates before the archive leaves the folder, and still
   write `test-scenarios.md`: the import is a FIFTH step after the four gates, never a substitute for one, and a
   green import proves the objects were accepted — not that a single screen renders. What changes is the last
   mile only: step 6b pushes the archive and reads the per-object failure report, and steps 7/8 then state what
   the session actually drove instead of "nothing". You still open no browser, click nothing, and ask for no URL,
   realm, client or login — the token is the entire environment you are given, and it carries its own coordinates.

1. CLARIFY HIGH-BLAST-RADIUS UNKNOWNS UP FRONT — ask, do not silently assume. Before building, use
   AskUserQuestion to settle AT LEAST these three (doc 19 Phase 0 adds more for a PRD with a dashboard —
   ask those too; what is forbidden is asking about an ENVIRONMENT, see the ⛔ below): (a) the LANGUAGE SET — which locales, AND which is the
   DEFAULT/authoritative one (a wrong set re-touches every entity; ONE language means NO `localized` fields /
   no per-locale maps anywhere; set the default with `mrjun.py locale set-default` + put it first in `locales`
   — it round-trips as `tenant.json.defaultLocale`, see doc 20); (b) BRANDING — the customer + a LOGO for the
   mail/PDF templates (identify the customer, find the logo on the web, or ask; a neutral placeholder mark as
   fallback — doc 15); (c) SCOPE/DEPTH — which phases, how far. The old "ask OR record an assumption" is too
   weak for these three — ASK. (Phase 0, doc 19, which lists the same three.)

   ⛔ THREE, AND ONE ENVIRONMENT QUESTION — NAMED BELOW, AND NOTHING ELSE. Do not ask for a project URL, a realm, a client, a login, a
   localhost port, or where the logs are. You will not drive the UI, and without a token you will not import
   either (OP 0), so every one of those answers is input you would discard — which Operating Principle 5f
   forbids. Each of the three above changes what you AUTHOR; a URL changes nothing you can do, and even in
   the connected branch it is the TOKEN that carries the coordinates, never a question.

   ⛔ EXACTLY ONE ENVIRONMENT QUESTION IS ALLOWED, ASKED ONCE, IN THE SAME ROUND AS THE THREE, AND IT IS THIS
   ONE: *"do you want the finished project imported into a live project? if so, paste an MCP token; if not, I
   stay fully offline."* Take the answer and never return to the subject. It is the exception because the token
   does not ADD to the forbidden list — it REPLACES it: realm and client ride in its own signed claims, the

   URL, a realm, a client, a login, a localhost port and a log location stay forbidden with or without it.
   ⛔ STATE THE PRECONDITION IN THE SAME BREATH, or you have stalled the build on a question the user cannot
   act on: a token is minted ONLY from an admin/author browser session in the TARGET project — Settings ->
   Developer -> MCP tokens, on a `type == REPORT` project — so it is never self-service and never something you
   can obtain. Ask, then BUILD ON THE ANSWER YOU GET; "no token" is a complete answer and the offline branch is
   the default, not a fallback. Never wait for a token, and never ask a second time.

   The export you produce imports into a `type == REPORT` project created from the "Empty project" template.
   Say that in the hand-over so the user picks the right target; do not ask them which one it is.

2. DECOMPOSE, THEN BUILD + TEST EACH MODULE — AND MAKE "NOTHING SKIPPED" MACHINE-CHECKABLE. Break the PRD into
   epics -> user stories -> small buildable units, one row each in a `plan.json` coverage ledger (doc 26 §6/§6a).
   Build one unit, `validate`, fix; mark its plan row done; then the next. Do NOT author the whole project and
   validate once at the end. The plan is an EXECUTABLE CONTRACT: **`mrjun.py coverage --plan plan.json` FAILS
   (non-zero) if any planned entity/form/page/rule/workflow/template/role/scheduler/dashboard is missing or still
   untested** — the build is not done until it PASSES. This gate is what catches "shipped with zero workflows /
   half the forms". Keep `plan.json` + per-module status in a working folder; for a large PRD, orchestrate the
   research/verify fan-out with the Workflow tool or subagents (the authoring stays sequential — one workdir).

3. BUILD EVERYTHING THE PRD ASKS FOR — never silently downgrade. If the PRD describes a multi-step human process,
   author a real WORKFLOW (doc 07), not just lifecycle actions — a project with zero workflows for a process-heavy
   PRD is a defect. If it describes reports/dashboards, HOME must actually RENDER them (charts visible), not
   redirect to a blank shell (doc 21/22). If it implies notifications/printouts, the mail + PDF templates must be
   BRANDED (customer logo) and as polished as the platform's standard/seed templates (doc 15) — a bare `<div>` or
   a blank scaffold is a defect.

4. THE FINISH LINE IS A MACHINE-CHECKED BUILD PLUS A HAND-OVER SOMEONE ELSE CAN DRIVE. `validate` green,
   `crud verify --db` green against a throwaway Postgres, `coverage --plan plan.json` green, and step 5b's
   independent re-derivation finding nothing the build lacks — THEN it is done. A green `validate` on its own
   is a candidate, not a deliverable: it proves the files are shaped right and nothing else.

   What the offline gates cannot reach — a page that opens without its layout chrome, a form whose dropdown
   comes back empty, a chart that renders blank, a predicate that is silently false — is REAL, and it is why
   `test-scenarios.md` exists and why it must be exhaustive rather than a sample. You are not the one who
   finds those; you are the one who makes them findable in one pass by someone who did not read the PRD.
   (doc 23 for the bug classes and the live-debug loop the USER runs; doc 26 for the gate ladder.)

5. THINK IN BUSINESS TERMS, NOT IN TABLES. The platform makes it easy to publish a screen per table and call it
   a project. That is a defect: the user judges the result by whether their WORK gets done, not by whether every
   column is on screen. Spend real thinking time here — before authoring a screen, be able to say in one line
   WHO does it, WHEN, and WHAT business event it records. If you cannot, it is decoration; drop it or ask.

   a. LIFECYCLE BEFORE SCREENS. For every entity: which states exist, who moves it between them, what is
      forbidden in each. A state is a contract, not a label — it gates row actions, filters what pickers may
      offer, decides what reports count, and is usually pinned by a DB CHECK constraint. Adding one state value
      is therefore a cross-cutting change: the CHECK, every predicate that compares the state, every enum/label
      map (in BOTH the node model and its settings mirror), every report/query/printout that filters on it.
      Enumerate those sites before you touch anything; a missed one silently drops records out of a report.
   b. EVERY LOCKING STATE NEEDS A WAY OUT. If a state hides edit/delete (a record "in approval", "locked",
      "closed"), an authorized action must exist to leave it — otherwise an interrupted process leaves records
      permanently stuck. State plainly what that escape does NOT do (e.g. it cannot terminate a running engine
      instance) and how the user completes the cleanup.
   c. GROUP BY BUSINESS AFFINITY, NOT BY TABLE. Put on ONE page (as tabs) what one person handles in one
      sitting — a register and the approval queue over the same documents, a catalogue and its price list, a
      case and its evidence. Keep apart what belongs to different roles or different moments. A tab set is an
      answer to "what is this workplace", not "how many tables did we make". Two tabs that no single user ever
      opens together are two pages.
   d. DO NOT INVENT PROCESS THE BUSINESS DOES NOT HAVE — and do not leave a process bypassable. Asymmetry is
      normal (a document that merely records an external fact needs no approval; the one that commits the
      company may). If you DO add a route, decide what happens to the direct action that does the same thing:
      remove it, gate it by role, or accept — explicitly, in writing — that the route can be skipped in one click.
   e. ONE ENTRY POINT, ONE FORM. When the same form is reached from two places that MEAN different things
      (create a new record vs. act on an existing one; a clerk's intake vs. an approver's review), author two
      forms and select them by predicate (doc 06), instead of bending one form until both cases are mediocre.
      One form group wired to BOTH a workflow user task and a crud-table row action is the exception, and
      it is normal: the same decision offered from the worklist and from the row. Then the rule must read
      BOTH, ATTRS FIRST, then the row — on the task path the attrs hold what was just typed and the row is
      at best stale (usually it is not seeded there at all and the read THROWS); on the table path the attrs
      are empty and the row IS the typed value:
          def FORM = { alias, field ->
              def v = context.data.getAttr(field)
              if (v != null) { return v }
              def row = null
              try { row = context.<ctx>."${alias}".data.get() } catch (Throwable ignored) { }
              return (row instanceof Map) ? row[field] : null
          }
      That is why the row read stays inside the try/catch: off a crud form it THROWS `No CRUD data available
      for CRUD: <alias>` (invariant below).
   f. NEVER ASK FOR INPUT YOU WILL DISCARD. If a branch ignores what the user typed, either do not ask (drop the
      mandatory flag, default the value server-side) or make it matter. A field the user is forced to fill and
      the code then throws away is the same defect class as a setting that renders but does nothing.
   g. IDENTIFY, THEN PREFILL. When the user names an existing record (picker/autocomplete), load it WHOLE —
      header and child rows — into the form instead of making them retype it, and re-bind when they pick another
      one (doc 02, the event-mapping prefill recipe).
   h. IF IT RENDERS, IT MUST WORK. Any control, action or setting visible in the UI must have a runtime
      consequence. Ship nothing whose only behaviour is being drawn.

6. DIVIDE THE WORK BY ARTIFACT, NOT BY JOB TITLE. Do NOT role-play a team ("as the PM I will now…", a business
   analyst, four Groovy developers, a dashboard specialist). A title adds no capability, costs context you need
   for routing, and produces narration that reads like rigour while checking nothing — the exact failure this
   contract exists to prevent. What measurably raises quality is a reader that did not have to hold the whole
   library, and a checker that did not build the thing. Three shapes, and only these:
   a. READ IN PARALLEL. Before a phase, fan out one agent per doc-cluster with a CONCRETE question ("for this
      PRD, from 04+05: which CRUD becomes a tree, and what is the exact columnSettings JSON"). Each returns
      decisions and literal JSON shapes, never a summary. This is the only way a multi-megabyte library fits
      inside one build.
   b. AUTHOR SEQUENTIALLY. There is ONE mutable workdir; concurrent `mrjun.py` edits race and corrupt each
      other. Never parallelise authoring. The exception is an artifact that lands in its OWN file — a pdfme
      template, a chart config, an HTML component — generate those in parallel, then apply them one at a time
      and `validate` after each.
   c. VERIFY INDEPENDENTLY, AND WITH DIFFERENT LENSES. N identical checkers find what one finds. Give each a
      distinct lens — does it render / does the rule actually fire / is it theme-safe / does the SQL bind as a
      string — and take the majority verdict on a disputed finding. The checker must not be the author: an
      agent re-reading its own reasoning confirms it.
   The tell of theatre: output that narrates a process instead of naming a file, a command, or an invariant.
   If a "role" cannot be handed an acceptance criterion, it is decoration — drop it.

7. THE BUILD IS LONGER THAN YOUR CONTEXT. Plan for that from the first command, not when you run out.
   a. SIZE. The library is megabytes of prose and `branches.json` inside a real project is megabytes of JSON —
      you will never read the file you are authoring, and you must not try. Route into the docs (19 -> 13 -> the
      specific reference); edit only through `mrjun.py`.
   b. SCALE, so you know when you have stopped rather than finished. A comparable delivered project of this kind
      runs to roughly 90 pages, 20 dynamic CRUDs, 180 rules, several workflows and schedulers, three locales —
      and got there over THREE import-and-drive iterations. If what you built is an order of magnitude smaller
      than the PRD implies, both gates can still be green and you are not done.
   c. RESUME RECORD — THREE artifacts, and the third is the door to the other two.
      `build-plan/plan.json` + `<workdir>-case/` hold the CONTENT: which module is done, which unit is next,
      what was decided and why. Write them as you go, never at the end; before a compaction or a handoff,
      update the plan rows, add a case note for anything decided this session, and name the next unit.
      But a fresh session reads NEITHER of them on its own — it reads `CLAUDE.md` and one skill description,
      and nothing else, before you get a word in. So the third artifact is the ENTRY POINT that points at the
      first two, and step 7b generates it from them rather than duplicating them. Do not hand-write it and do
      not let it say anything `plan.json` and the case notes do not: a map that disagrees with the territory
      is worse than no map, because it is believed.

0. READ THE MODE BEFORE YOU TOUCH ANYTHING. If `./.dokie/project.json` exists in the working folder, read it and
   take the mode from its `mode` field; if there is no such file, the mode is a fresh BUILD and step 1 follows as
   written. This is step 0 and not part of step 1 because the mode decides whether there is a base to unpack at
   all: a BUILD unpacks `empty.mrjun` and authors on it, while a SUPPORT session is already bound to a live
   project and to the `./work` that mirrors it — unpacking a fresh base over that is how a one-field change
   request becomes a rebuild that replaces the customer's pages. The same file names the project the folder is
   bound to; a token, if there is one, lives beside it and is gitignored — never echo it into a reply and never
   write it into a file you ship. The support delta is 28-support-mode-over-mcp.md.
   ⛔ IF THE MODE IS SUPPORT AND `./.mcp.json` DOES NOT EXIST, ASK FOR THE CONNECTION — ONCE, FIRST, BEFORE
   ANY OTHER QUESTION. One folder is one project talking to one tenant, so the connection belongs to the
   folder and nothing else can supply it: *"this folder has no MCP connection yet — paste the block from
   Settings → Developer → MCP tokens of the project you are supporting."* Then:
        <paste> | python3 ./builder/tools/mrjun.py handoff mcp --project ./work
   The command normalises whatever was pasted, writes `./.mcp.json` mode 600 and git-ignores it. ⛔ Do NOT
   write that file yourself and do NOT echo the credential back — not in a reply, not in a note, not in a
   commit. Then STOP and say: restart Claude Code once in this folder and approve the server. MCP servers
   connect at session start, so the session that wrote the file cannot use it, and pretending otherwise
   wastes a turn per tool call. ⛔ And if `./.mcp.json` IS there, the connection is configured — never ask
   again; asking twice for something already answered is the failure this step exists to prevent.
0b. SUPPORT MODE — OFFER THE LIVE TEST, once, after the connection is up. The MCP channel reads and writes
   OBJECTS; it cannot tell you whether what a person opens actually works, and a page that renders empty or a
   rule that denies everyone passes `validate` every time. So offer to drive the running project in a real
   browser: *"I can test this live — drive the scenarios in a browser and fix what I find over MCP. It will
   create test records, and test roles if the scenarios need them, in the real project. Want me to?"* It is an
   OFFER; wait for a yes, because it acts on a running tenant. On yes:
        python3 ./builder/tools/mrjun.py handoff browser --project ./work   (merges; keeps the tenant server)
   ⛔ Install a missing `node`/`npx` yourself — the command prints the line — then restart Claude Code once.
   ⛔ OPEN THE PROJECT, NOT THE INSTALLATION — `<root>/<realm>/<client>`, e.g. `http://host:8077/saas/ardshin2`.
   The bare root bounces to `…/auth;jsessionid=…`, which renders none of this project. realm/client come from
   the MCP TOKEN's own claims (or `.dokie/project.json`); only the root cannot be derived — the MCP endpoint is
   a different service on a different port. If `.dokie/project.json` records `project.liveUrl`, USE IT and ask
   nothing; otherwise ask ONCE for the origin and record it with `handoff emit --base-url http://<host>:<port>`
   so no later session asks again. `handoff browser` prints the resolved address or names the missing half.
   ⛔ THE HUMAN LOGS IN. Never type a password, never ask for one: open the URL and ask them to sign in, in
   that window, as a user holding the AUTHOR role — author is the role that can create roles, so with it you
   build every other identity the scenarios need. The full loop, the scenario file, the negative cases and
   what must never be driven against real records: 28-support-mode-over-mcp.md §8.
1. UNPACK / INSPECT. If given a `.mrjun`: `python3 tools/mrjun.py unpack <file.mrjun> <workdir>`. Then ALWAYS
   `mrjun.py inspect --project <workdir>` to see the current state. Base a brand-new project on the `empty`
   export (a REPORT-typed scaffold).
2. DETECT THE SCENARIO (19-build-decision-procedure.md, Phase 0):
     A — EMPTY project + a PRD -> build from scratch (phases 2->14).
     B — a populated business schema + UI already in the dump but NO dynamic-cruds.json -> wire dynamic CRUDs
         over it (primary guide: 18-existing-schema-to-dynamic-wiring.md).
     C — a FILLED working dynamic project + a change request -> run the Scenario-C delta loop (locate ->
         minimal delta -> apply only the delta -> re-validate). Do NOT rebuild what you were given.
         The EXECUTION CHANNEL is a SUB-decision of C, never a fourth scenario: with NO token the delta ships as
         FILES (edit `./work`, re-pack, the user imports); with the `./.dokie/project.json` marker AND a token it
         is DUAL-WRITE — edit `./work`, `validate`, then write that ONE object live and read it back
         (28-support-mode-over-mcp.md). The delta is identical either way; only where it lands differs, and
         picking the channel first is how a support request stops turning into a rebuild.
2b. CLARIFY FIRST (Operating Principle 1). Before authoring, settle the high-blast-radius unknowns with
   AskUserQuestion — LANGUAGE SET, BRANDING/logo, SCOPE/depth (Phase 0, doc 19). These change every downstream
   file; deciding them wrong is the single most expensive kind of rework.
3. DECOMPOSE, THEN FOLLOW THE DECISION SPINE. First run Phase 1 **and Phase 1a** (doc 19): decompose the PRD
   into the entity/actor/document/status/report/notify/process inventory AND the **TRIGGER inventory** — what
   STARTS each process, exactly one of `FORM` / `SCHEDULER` / `CRUD METHOD` / `SERVICE TASK`. Sweep the PRD a
   second time for every sentence whose actor is the SYSTEM ("nightly", "if no response within N days", "when
   the status becomes X"): the answer an unasked trigger question gets is always "a person on a screen", so a
   blank column ships as a start form nobody was told to press, and a trigger whose product is a CASE is a
   WORKFLOW START, not a mail (doc 27). Then decompose further into epics -> user stories -> small buildable
   units with a working-folder task graph (doc 26). Then work 19-build-decision-procedure.md phase by phase; for
   each phase DECIDE (with its defaults), AUTHOR (via the doc it points to + the mrjun.py command), and satisfy
   its DONE-WHEN gate before moving on. Build + `validate` each unit as you go (Operating Principle 2) — never
   author everything then validate once at the end. The build/write order + dependency graph is 13-master-playbook.
3a. PUT THE PRD'S GAPS TO THE USER, AND OFFER WHAT IT DID NOT THINK TO ASK FOR — ONCE, IN TWO LISTS.
   LIST A = the PRD's own gaps and contradictions (below). LIST B = things the PRD does not ask for that
   you would add anyway (3a-bis). Both go in ONE round, before you author anything. A is answered; B is
   TICKED.

   ⛔ SUPPORT MODE SKIPS THIS ENTIRE STEP — both lists. The round happened at BUILD time and its answers are
   already in the project; re-running it re-opens settled decisions and asks the user to re-approve their own
   system. Locales, branding and scope are then not questions at all: READ them from the live project instead of
   asking, and put only the CHANGE REQUEST's own gaps to the user.

   LIST A — GAPS AND CONTRADICTIONS, WITH A RECOMMENDATION ON EACH.
   A PRD is a business document. It is written by people who know the business and not the platform, so it
   will leave things open, and it will occasionally ask for two things that cannot both be true. Building
   over that silently is how a project comes out technically green and businessly wrong — and the person
   who could have settled it in thirty seconds never got asked.
   So: once, after the Phase-1 inventory exists and BEFORE you author anything, produce ONE consolidated
   list. Not a stream of questions during the build, and not a private assumption log: one pass the reader
   can answer in a sitting.
   Each item carries five things, in this order:
     - WHAT THE PRD SAYS — quote or cite the clause, so the reader can check you read it right;
     - WHAT IS OPEN OR CONTRADICTORY — the gap in the PRD's own terms, not in platform terms;
     - WHAT YOU PROPOSE — one concrete option, named;
     - RECOMMEND / DO NOT RECOMMEND, and WHY — take a position. "Either could work" is not an answer; you
       have read the whole PRD and they have not read the platform, so the judgement is yours to offer;
     - WHAT IT COSTS TO SKIP IT — what the delivered project will not do, in business terms.
   Sort by blast radius: an item that re-touches every entity comes before a nicety. Use AskUserQuestion
   for the items whose answer CHANGES WHAT YOU BUILD, and put the rest in the list as stated assumptions.
   ⛔ Silence is not consent. An item nobody answers ships as an assumption written into the hand-over in
   the user's own words — never as a decision you quietly made for them.
   ⛔ This is about the BUSINESS, never about an environment. Do not ask for a URL, a realm, a client, a
   login or where to test — Operating Principle 0 settles all of that, and asking hands your job back.
   Typical members of this list, from real PRDs: a status named in one clause and absent from the state
   list; a role that acts in a process but is missing from the role table; a document the process produces
   that no screen ever shows; a deadline with no clock to enforce it; an approval whose rejection path is
   never described; a report the PRD asks for whose data nothing in the PRD records; two clauses that
   disagree about who approves what. Each of those is a one-line question and a one-line recommendation.

3a-bis. LIST B — WHAT YOU WOULD ADD THAT THE PRD NEVER ASKED FOR. CHECKBOXES, OPT-IN, DEFAULT OFF.
   List A is about what the PRD got wrong. List B is about what it never thought of. A PRD is written by
   people who know the business and have never seen the platform, so they cannot ask for what they do not
   know is nearly free — an audit trail, a worklist, an overdue clock, a printable form of a document they
   only described on screen. Those are not gaps in their document; there is nothing to correct. They are
   OFFERS, and the only honest way to make an offer is to let the reader decline it.
   So send them as a MULTI-SELECT AskUserQuestion — a checkbox list. One question, several boxes, tick what
   you want. Each box is one line the reader can judge without knowing the platform:
     - WHAT IT IS, in business words — "every status change recorded with who and when", not "an audit CRUD";
     - WHAT IT BUYS — the business question it answers or the failure it prevents;
     - WHAT IT COSTS — roughly, in build terms ("one table, one page" / "a workflow branch and a template");
     - RECOMMEND / DO NOT RECOMMEND, and why. Offer things you would NOT recommend too, when the PRD's
       shape suggests the reader may be expecting them — saying "you could have this, I advise against it,
       here is why" is worth more than silently not mentioning it.
   ⛔ DEFAULT OFF. An unticked box is NOT BUILT — no partial version, no scaffold "in case". It goes into
   the hand-over under "offered and declined", so the next person knows it was a decision and not an
   oversight. Never build an offer that was not ticked, and never treat no-answer as a yes: List B is the
   one place where silence IS a no, precisely because it is not the PRD's own scope.
   ⛔ A TICKED BOX BECOMES A PLAN ROW. Add it to `plan.json` like any PRD requirement, so `coverage` fails
   the build if you then skip it. An offer accepted is a promise, and the anti-skip gate is what keeps it.
   ⛔ NEVER PUT THE PRD'S OWN CONTENT IN LIST B. Anything the PRD asks for is mandatory (Operating Principle
   3) and is not a checkbox. Turning a PRD requirement into an offer is how a build gets silently
   downgraded with the user's own click as cover — the single worst failure this whole step can produce.
   ⛔ KEEP IT SHORT AND RANKED. At most about eight boxes, best value first. A list of thirty makes the
   reader tick nothing, or tick everything without reading — both are worse than not asking.
   ⛔ BUSINESS ONLY, same as List A. Never offer an environment, a tool, a refactor of your own workflow, or
   anything the reader cannot evaluate as a business outcome.
   Typical offers, from real builds: an audit/history trail on the entities that change hands; a worklist
   page for a process the PRD describes only as prose; an overdue/SLA clock and the scheduler that ticks it;
   a PDF of a document the PRD only shows on screen; a dashboard tile for a number the PRD asks people to
   compute by hand; a role group split the PRD implies but never names; a lookup table for a field the PRD
   spells out as free text; a rejection/return path for an approval that only describes the happy road.
   ⚠️ The CHART conversation is the same round, and doc 22 §2A already governs it: the charts a spec names
   are a FLOOR, so proposed extra charts are List B boxes and objections to specified ones are List A items.
   Do not run a separate chart round.

3b. ⛔ DO NOT REIMPLEMENT A TOOLKIT PRIMITIVE. If you write a generator, IMPORT from `tools/mrjunkit/core.py`
   (`core.regen_ids`, `core.looks_uuid`, `core.iter_nodes`, `core.new_rep_object`, `core.set_inner_json`, …)
   and `tools/mrjunkit/db_cmds.py` (`db_cmds.normalise_rows`, `db_cmds.dump_cell`, `db_cmds._build_ddl`).
   Both blank-page disasters of 2026-08 came from one generator hand-rolling its own `regen_ids` with a
   hardcoded allowlist of "symbolic" ids, when `core.regen_ids` already encodes the correct, general rule:
   **regenerate ONLY uuid-shaped identifiers; every non-uuid identifier is a layout anchor the runtime
   resolves BY NAME — keep it verbatim.** A reimplementation is a silent fork of a rule you did not know all
   of. Build pages with `page add` + `node add` wherever possible; when you must clone, clone with
   `core.regen_ids`.
4. PREFER `mrjun.py` COMMANDS over hand-writing JSON — the toolkit enforces the hard rules and cannot malform the
   files. Consult the doc, then run the command. Hand-write JSON only where no command exists (complex BPMN
   gateway logic, per-field form-control settings, tab layouts, PDF template content, schedulers) and then follow
   the EXACT export shape documented in the relevant file. If a command produces a wrong-shaped result (e.g. the
   nav-label / localization traps), fix the toolkit or the output — do not ship the defect.
5. VALIDATE + COVERAGE (offline gates — necessary, NOT sufficient). `mrjun.py validate --project <workdir>` -> no
   NEW errors (warnings about pre-existing platform-internal orphans are acceptable). ⚠️ The bundled BASE is not
   clean — `initialtemplates/empty.mrjun` validates with warnings and one pre-existing error, and
   `initialtemplates/empty-validate.txt` records its exact output: diff against that file rather than chasing a
   finding you did not introduce; it also runs schema-aware
   dynamic-CRUD checks (CHECK-literal / expression-coverage incl. list sub-grids / document-delete-cascade /
   enum-option snapshots) and the PLATFORM-CONTRACT checks — the two failure classes that used to be found
   only by importing and clicking, and that a build you never run has no other way to catch:
     - **an object the platform will REJECT at import.** Fields the platform's DTOs declare mandatory,
       checked against the archive: a query with a blank `name`/`query`, a workflow or role group with no
       name, a source missing its connection fields. Objects import in a fixed order, so one rejected query
       can cost every workflow, rule, context, form and setting behind it — the project then arrives with a
       database and blank screens. The usual cause is a scaffolded CRUD whose `create`/`update`/`delete`
       later became GROOVY: their paired query records are never filled and ship as `"query": ""`.
     - **a Map argument meeting a single-slot SQL method that the map does not name.** The executor then
       binds the whole serialized map into that one slot. On a scalar column it is a loud
       `invalid input syntax for type …`; on a text column it is silent and the screen just shows nothing.
       This is the default shape of `count` on a table with exactly one filter. The gate reads GROOVY
       callers only — the table plugin builds its filter map at runtime, so a green gate proves your
       rules are safe, not that the table is.
   Then `mrjun.py coverage --project <workdir> --plan build-plan/plan.json` -> **PASS** (every planned item
   built and marked done — the anti-skip gate, doc 26 §6a).
   Then `mrjun.py crud verify --db "<conninfo>" --project <workdir>` — REQUIRED, not optional, and named as
   one of the four gates in Operating Principle 0. It executes every SQL method against real/seeded rows, so
   CHECK / NOT NULL / FK actually fire; it is the only gate that runs your SQL. It needs a `psql` binary and
   ANY throwaway Postgres — not the platform, not the customer's database — so "I could not reach the DB" is
   a reason to start a container, not a reason to skip it (doc 26 §3a).
   ⛔ THREE THINGS THESE GATES CANNOT SEE — know them or you will trust a green run:
     - **Nothing here parses or compiles Groovy.** `validate` checks a rule is referenced and shaped right;
       `crud verify` runs SQL methods only and skips GROOVY ones. A syntax error passes every offline gate, and
       an unbalanced body makes `validate` skip its OTHER checks on that rule. Only a live execution finds it.
     - **`coverage --emit` self-certifies.** It derives the plan FROM the build, so a plan emitted afterwards
       always passes. The gate means something only when the plan was written from the PRD. `status:"deferred"`
       likewise downgrades any missing row to a warning — an escape hatch, not a pass.
     - **`coverage` never opens what it counts.** It matches by alias/name, so an empty shell satisfies a row.
       Grep the rule body before you mark it done.
5b. INDEPENDENT ACCEPTANCE — REQUIRED before you call the build complete. Have an agent that did NOT build it
   re-derive, FROM THE PRD ALONE, the inventory of entities, actors, documents, statuses, processes and the
   TRIGGER of each process — then diff that against `plan.json` and against what is actually in the workdir.
   This is the only check that catches a plan which quietly matches a smaller project than the PRD describes,
   and it is what `coverage` structurally cannot do for itself. Anything the re-derivation finds and the build
   lacks is a defect, not a scope decision — raise it with the user rather than closing it silently.
6. PACK, AND SAY WHAT HAS NOT HAPPENED. `mrjun.py pack <workdir> <out.mrjun>`.

   ⛔ WITH NO TOKEN — THE DEFAULT, AND EVERY WORD OF IT STANDS:
   ⛔ Do not import it. Do not ask for somewhere to import it. You have no platform and you are not getting
   one; the user has a project, knows its realm and client and login, and drives it themselves with the file
   you write in step 7. What you owe them here is not an attempt — it is an unambiguous sentence in the
   hand-over: *this export has not been imported or run anywhere; the four offline gates are green; here is
   what to click first.*

   ⛔ THE HAND-OVER ALSO CARRIES THE STEP-3a LEDGER — two short sections, always, even when both are empty.
   **"Assumed, because nobody answered"**: every List A item that went unanswered, written as the assumption
   it became, in the user's own words. **"Offered and declined"**: every List B box that was NOT ticked, one
   line each. Without the second section a declined offer is indistinguishable from something you never
   thought of, and the next person re-litigates it — or worse, files it as a defect.

   That sentence is the whole point. A build described as "done" that was never run reads as tested, and the
   user finds out the hard way. A build described as "gated offline, not yet driven" sets them up to spend
   twenty minutes on the sweep in `test-scenarios.md` §a and find the layout, dropdown and locale faults the
   file gates structurally cannot see (doc 23).

6b. IMPORT — ONLY IF A TOKEN WAS GIVEN. There is no half version of this step: with no token, skip it entirely
   and step 6 is the end of the build. With one, do all of it, in this order.
   ⚠️ NOT YET AVAILABLE ANYWHERE — READ THIS BEFORE THE REST OF THE STEP. As of CONTRACT-VERSION 2 the
   import tools named below (`nct_project_import_start`, `_status`, the snapshot pair) and the toolkit's
   `push --mcp` do NOT exist yet: no platform serves them and `mrjun.py --help` does not list it. The step
   is written out in full because it is the contract the two halves are being built against, and because a
   later platform will have them — not because you can run it today.
   So the ONLY correct behaviour right now, and the first thing to do even after they ship: list what the
   connection actually offers and look for `nct_project_import_start`. If it is absent — which it is today —
   say so plainly, hand the file over exactly as the offline branch does, and ⛔ do NOT improvise a
   substitute: not another tool, not a chunk of base64 through a tool call, not a shell command against the
   platform. A missing tool here is a platform version, not a failure of your build, and the user's next
   step is the manual import in GETTING-STARTED.md §6.
   a. ⛔ VERIFY THE TARGET IS `type == REPORT`, AND REFUSE OTHERWISE. Read the type back from the live project
      (`nct_project_getCurrentInfo`) BEFORE you push a byte. A non-REPORT target does NOT no-op: the import
      skips the sources, the `project-db.dump` restore and all nine object writers — and then goes on to REPLACE
      EVERY PAGE AND EVERY BRANCH with yours. The project is left holding your screens and not one of the
      queries, rules or forms they reference: every page dead, and nothing reported an error. Refuse, name the
      type you read, and tell the user to create the target from the "Empty project" template.
   b. SNAPSHOT FIRST (`nct_project_tag_snapshot`), and refuse to import if the snapshot fails. Import REPLACES,
      it never merges, and that tag is the only way back (`nct_project_tag_revert`) — including back from a
      half-applied run.
   c. ⛔ PUSH THE ARCHIVE WITH THE TOOLKIT — `mrjun.py push --mcp` — NEVER by pasting the file into a tool call.
      A real `.mrjun` is megabytes, base64 of it is millions of characters, and you cannot emit that: the attempt
      burns the session and produces a truncated archive. The toolkit uploads the bytes over its own HTTP channel
      and prints a HANDLE; the handle is the only part of the file that travels through you.
   d. START THE IMPORT WITH ALL THREE BUSINESS-LOGIC FLAGS STATED EXPLICITLY — `replaceBusinessLogic`,
      `rebuildSchemas`, `recreateIntegration` on `nct_project_import_start`. There are no defaults; a flag you
      did not state is a decision you did not make, and the wrong one silently keeps the old schema or the old
      integration under your new objects. Record the three values you passed in the hand-over.
   e. POLL `nct_project_import_status` TO A TERMINAL STATE. It is keyed by (realm, client), NOT by a run id, so
      check its `startedAt` against your own push — otherwise you read a colleague's finished import as your own
      and report a success you never caused.
   f. READ THE PER-OBJECT FAILURE REPORT and repeat it, object by object, in the hand-over. ⛔ `DONE` IS NOT
      PROOF THE PROJECT ARRIVED: mail and PDF templates are written outside that reporting and fail with a log
      warning only, so an import can report `DONE` with not one template in the project. Say so plainly, and
      keep step 7 exactly as it is — an import is not a run, and nothing here clicked a single screen.

7. WRITE THE TEST SCENARIOS — a `test-scenarios.md` BESIDE the finished `.mrjun`. The person who tests this is
   not you and did not read the PRD twice; they open the running application and need to know what to press, what
   should happen, and — above all — WHAT ELSE should have changed. The export alone is not the deliverable; this
   file ships with it, always. Write it in the language the user is speaking to you in.

   ⛔ EXHAUSTIVE, NOT A SAMPLE. Do not write "the main scenarios". Build the list from a MATRIX and walk it:
   every entity × every action × every state it can be in, every process × every branch, every role × every
   screen. Cross-check it against `plan.json`: every action, rule, workflow, template and dashboard row there
   must appear in at least one numbered scenario, and every state transition you authored must be exercised at
   least once. A scenario list shorter than the build is a gap in the testing, not brevity. Never write "etc.",
   "and so on", or "similar for the rest" — the tester cannot expand those.

   a. ONE SECTION PER ROLE — who logs in, what that role must see, and what it must NOT see. A role that can
      reach something it should not is a finding the tester can only make if you told them the boundary.
   b. EVERY PROCESS, END TO END, DOWN EVERY BRANCH. Approve AND reject AND return-for-revision AND timeout —
      a process tested only down its happy path is untested. Name who performs each step so the tester knows
      when to switch user.
   c. ⛔ THE RIPPLE — WHAT ELSE CHANGED. This is the most valuable part of the file and the one a tester cannot
      reconstruct alone, so give it its own column or block in EVERY write scenario: the user did X here, so
      WHAT MOVED SOMEWHERE ELSE? Enumerate, per action, the consequences you actually built:
        - which list, counter, badge or dashboard number moves, and in which direction;
        - which record changes STATE, and what that state now forbids or allows;
        - whose worklist gains or loses a task, and whether it is visible to a NON-admin member of that group;
        - which notification fires, to whom, and which printout becomes available;
        - which picker/dropdown elsewhere stops offering — or starts offering — that record;
        - which report, chart or filtered view now returns a different row count;
        - which parent/child rows were touched by cascade (a header change that rewrites its lines; a delete
          that must take its children or must be refused because of them);
        - what a SCHEDULER or a service task will do to this record on its next run.
      Write each as something checkable in a NAMED other place: "after approving, open Screen B — the row must
      have left the 'Pending' tab and the Home counter must drop by one". A consequence the tester cannot go and
      look at is not a test.
   d. THE BACKWARD RIPPLE. Reject, revert, cancel, delete: every consequence in (c) must be shown to UN-happen —
      or to deliberately persist, if that is the design. This is where half-built lifecycles surface.
   e. REFERENCE-DATA CHANGES. Rename or deactivate a lookup value, a role, a user, a category: where does the
      OLD label survive on existing rows, what happens to records that pointed at it, and does a deactivated
      value still appear in pickers or only on historical rows?
   f. THE PROHIBITIONS. For each lifecycle state: what must be IMPOSSIBLE there (edit a locked record, delete an
      approved one, skip an approval, act as the wrong role). Testing that something is refused catches what
      testing that something works never will.
   g. ORDER, REPETITION AND CONCURRENCY. The same action twice (an automatic trigger must be run TWICE and still
      produce exactly ONE case); steps taken out of order; the same record open in two tabs and saved from both;
      a process started while a previous instance is still open.
   h. THE EMPTY AND FIRST-TIME STATES. No rows yet, no results for a filter, a picker whose source is empty, the
      very first record of an entity, a user with no assignments.
   i. EVERY NOTIFICATION AND PRINTOUT: what triggers it, who receives it, what it must contain, is it branded.
   j. THE DASHBOARD: which number on Home comes from which data, so the tester can tell a right number from a
      plausible one — and which scenario in this file should make each number move.
   k. LOCALES: the same screen under each configured language, and the language switch itself.
   l. THE THINGS NO OFFLINE GATE CAN CATCH — list these explicitly, because they are exactly what the tester is
      for and they look fine until someone clicks: a page that opens with no menu or header; a dropdown that is
      empty or says "No results found"; a form that reports success while the value does not change (⛔ tell them
      to RE-OPEN the row and read it back — a toast is not evidence); a task invisible to a non-admin member of
      the group; a screen under each of the five skins.

   Format each scenario so it can be executed and reported without asking you anything:
   **№ · Role · Precondition · Steps · Expected result · WHAT ELSE MUST HAVE CHANGED (where to go and look) ·
   What it proves**. Number them so a bug report can cite a number. Group by module, load-bearing first — the
   tester may not reach the end — and open the file with a short dependency map: for each entity, the other
   screens and numbers that react to it.
   ⛔ Be honest about provenance. You drove NOTHING — you have no platform (step 6) — so the file opens with
   one line saying so: *none of these scenarios has been executed; they are derived from the build, not from a
   run.* Then, per scenario, say which of the four offline gates covers it and which cannot: `crud verify`
   really did execute the SQL behind a create/edit action, and that is worth stating; nothing at all checked
   that a dropdown populates or that a page keeps its layout chrome. A list that reads as tested when it was
   only authored transfers your uncertainty to someone who cannot see it — which is worse than no list.
   ⛔ IF STEP 6b RAN, THE PROVENANCE LINE STAYS — it just tells the truth about what happened instead: *this
   export was imported into <project> at <time>; the import reported <status> with <n> object failures; NO
   scenario below has been executed — an import is not a run.* Write what the session actually drove and not one
   word more. An import proves the objects were accepted and says NOTHING about a page keeping its chrome, a
   dropdown populating or a rule firing — which is the entire subject of this file, so the sweep in §a is still
   the tester's first job.

7b. LEAVE THE FOLDER RESUMABLE — one command, and it is not optional:

        python3 ./builder/tools/mrjun.py handoff emit --project ./work --mode build|support

   It regenerates `CLAUDE.md`, ONE skill under `.claude/skills/`, and `.dokie/project.json` from
   `build-plan/plan.json`, the case notes and the export itself. Run it LAST, after the plan rows are
   final, and re-run it after any later change — it is idempotent, so a re-run with nothing changed
   produces byte-identical files and a diff always means a real change.

   Why a command and not a paragraph you write yourself: the next session is a DIFFERENT session with no
   memory of this one, and the only things it reads before you can tell it anything are `CLAUDE.md` and the
   skill's one-line description. A folder that leaves them unwritten hands the next person a 2.7 MB library
   and no map — they re-derive the routing, the global parameters and the coordinates from scratch, and the
   first thing they get wrong is the one you already solved. Writing them by hand is worse than not writing
   them: hand-authored context drifts from `plan.json` the moment either changes, and a confidently wrong
   map costs more than none.

   ⛔ Three things this command must never be talked into. **No credential in any emitted file** — the token
   is registered with the CLIENT and never lands in this folder at all; a `Bearer ${VAR}` in a config is the
   trap, because an unset variable expands to the literal placeholder, the client still reports the server
   as connected, and every call 401s where nobody is looking. **No executable hook**, ever: a
   non-interactive run bypasses the folder-trust prompt and would execute one silently, and this folder is
   handed between people. **ONE skill, not one per module** — a skill's description is in context on every
   turn whether it is used or not, so a folder full of them re-creates, on the client side, exactly the
   budget problem that makes a large tool list unusable.

======================================================================
Every invariant carries a CHANNEL TAG. [BOTH] = true whether you ship a file or write live over MCP. [FILE] =
about the shape of the export ARCHIVE, and meaningless over MCP. A third tag, [MCP-ENFORCED], is reserved for a
rule the server refuses for you on that channel so it is yours to obey only in the file — and as of
CONTRACT-VERSION 2 NOTHING carries it, because no server-side check of these rules exists yet. It is listed so
that the day one lands, the tag is already defined rather than invented. The tag never weakens the rule — it
says where the rule can bite you, and when in doubt a rule is tagged [BOTH], which is the safe direction.
- ⛔ [BOTH] CHANGE-REQUEST SAFETY — when the user asks to CHANGE an EXISTING project/`.mrjun` (not build fresh), make

  `branches.json` / `dynamic-cruds.json` entries (e.g. `zip <archive> rep-objects.json branches.json`), leaving

  SHAPE BLOCK — never from what the field "should" be called. Import deserialises with Jackson
  `FAIL_ON_UNKNOWN_PROPERTIES=false`, so **an invented key is dropped in complete silence**: the object
  imports, appears in its list, and only the field it was meant to fill is empty. There is no error, no
  warning and no log line. The objects at risk are the ones every shipped `.mrjun` exports as `[]` —
  `schedulers[]` above all (12 §3.1), and any DTO the reference exports happen not to exercise. Before
  authoring one, grep the reference exports for a real instance; if there is none, open the doc's shape
  block AND the DTO class it names (`nct-transfer/.../<X>Dto.java`) and match them key by key. In 2026-08
  a scheduler shipped with `cronExpression` instead of `job.expression` and no `actionType`: it imported
  clean, showed an empty Action Type, and **never fired once**. `validate` now gates schedulers; nothing
  gates the next DTO you invent a name for.
- ⛔ [FILE] EVERY CELL OF `project-db.dump` `tables[].rows[]` IS A **JSON STRING** OR `null` — NEVER a JSON number
  or boolean. The restore reads the rows as `List<Map<String,String>>` and assigns each cell to a `String val`;
  generics are erased, so an unquoted `1` throws `class java.lang.Integer cannot be cast to class
  java.lang.String`. That is a `ClassCastException`, **not** a `SQLException`, so it escapes the per-table
  savepoint and unwinds the WHOLE schema: the user sees "Imported with warnings — The database was NOT
  replaced. Schema(s) [x] were rolled back", zero business rows land, and every table, chart and worklist in the
  project opens EMPTY. Typing is `columnTypes`' job (JDBC `java.sql.Types` codes), never the JSON type's —
  the driver turns `"1"` into an integer because the parameter is bound as `Types.INTEGER`. Booleans are
  `"true"`/`"false"`, jsonb is the JSON **as a string**, numerics are `"1200.00"`. Also: `columnTypes[]` and
  `sequences[].lastValue` are read as `Number`, so those must be unquoted. Route the rows through the toolkit
  primitive — `db_cmds.normalise_rows(columns, rows)` / `db_cmds.dump_cell(v)` — do not hand-roll it.
  A dump exported by the platform can never show this (it writes `val.toString()`), so **only a generated or
  hand-edited dump is at risk, and no reference export demonstrates the correct shape by contrast.**
  `validate` now ERRORs on it; it did not before, which is how a shipped build reached a customer's import.
- ⛔ [BOTH] EVERY SCREEN GETS A LAYOUT — the dashboard, and every FORM and FILTER BAR on every page. A form or a
  filter bar whose controls hang straight off its anchor renders one full-width block per field: a
  five-field filter becomes five stacked rows above the table. Wrap them: an `nct.html.plugin` whose markup
  is a `<div class="row">` of `<div class="col-md-N"><plugin id="…" name="nct.parsis.plugin"></plugin></div>`
  cells, one control per cell. Shapes: the FILTER BAR in 04-crud-table-plugin.md; the DATA-ENTRY FORM in
  03-generate-fields-from-crud.md (`gen_row_*` / `gen_colK_*` / `gen_slot_*`, `layoutColumns` 4 -> `col-md-3`);
  the DASHBOARD in 21-homepage-and-redirect.md §Home-as-dashboard. All three are hand-written HTML — there is
  no toolkit command that generates them. TABLES are the exception — a crud table lays itself out.
  ⚠️ `validate` sees only TWO of the three: the dashboard (ERROR on the front door — which it resolves through
  Home's `Redirect` — WARN elsewhere) and the filter bar (WARN). A DATA-ENTRY FORM'S LAYOUT IS NOT MACHINE-
  CHECKED — it is on you, and a green run says nothing about it.
- ⛔ [BOTH] A DASHBOARD IS COMPOSED, NOT EMITTED. The commonest failure is not a wrong chart — it is a GRID DUMP: six
  identical cards in a rigid 2-column grid, no title, no KPI strip, no section headings, every chart a plain
  vertical bar, `0.5 / 1.5` ticks on a count and `UNDER_INVESTIGATION` printed at a business audience. It
  passes every gate and it is a DEFECT. The shape that works, in full, with working code for the four
  recipes a grid dump never reaches: 22-charts-params-and-filters.md **§2B**. The floor:
    · a page TITLE plus one sentence saying what the board shows and that it filters on click;
    · a KPI STRIP first — 3-5 tiles, at least one gauge or rate, big type (Plotly `indicator`, §2B.4a/b);
    · SECTIONS with a heading and an icon, ONE card per section holding several charts — never one card per chart;
    · rows that DIFFER in chart count (4 / 3 / 2 / 3, not 2 / 2 / 2 / 2) and columns that are UNEQUAL inside a
      row (`col-xl-8` + `col-xl-4`), width chosen by the chart's shape (§2B.2);
    · AT LEAST FOUR distinct chart shapes on the board — indicator, doughnut, horizontal bar, combo dual-axis,
      stacked. Six vertical bars is one shape used six times;
    · theme-aware colours (`getComputedStyle(host).color`), `precision:0` on counts, a bn/mn/k formatter on
      amounts, humanised enum labels, click affordance.
- ⛔ [BOTH] EVERY CHART MAKES A COLOUR DECISION — colour is data, not decoration. Ask what the AXIS is, THEN pick the
  family: ordered-with-a-verdict (severity, RAG, SLA) -> traffic light mapped BY LABEL; identity (branch,
  channel, type) -> a qualitative palette, one hue per value; ordered magnitude with no verdict -> one hue,
  lightness stepped; signed around a real zero -> diverging with a NEUTRAL middle. Painting a nominal axis in
  red/amber/green invents a verdict; painting a risk axis in two blues is a defect that has shipped.
  ⛔ Never leave it to the library's default palette, and never use an INDEX array
  (`backgroundColor:['#..','#..']`) — that binds colour to row ORDER, so a cross-filter board repaints its
  survivors on every click. Map by label. ⛔ Same measure = same colour in EVERY cell of the board and on the
  drill target; loss is red everywhere or the page reads as unrelated pictures. And keep it BEAUTIFUL: ~4-6
  hues per board, one accent spent on the number that matters, a single-series ranked bar in ONE colour,
  transparent chart backgrounds. Decision table + the aesthetic rules: doc 22 §2B.6; palettes, verified hexes,
  contrast and colour-blind separations: §6.1.
  Run §2B.6's nine questions against your own screen before calling a dashboard done. Answer 9 is the real
  gate: would you put this screenshot in a proposal?
- ⛔ [BOTH] HOME MUST RENDER REAL CONTENT (charts), not a blank shell. If the PRD has a dashboard, either build the
  `chart.js.plugin` grid **into Home's own parsis** (preferred — no redirect that can land on nothing) or redirect
  Home to a dashboard page. A grid of empty `nct.html.plugin`
  cells ("Modify html") = the charts weren't placed/rendered — each grid cell's `<plugin id="X" name="chart.js.plugin">`
  must have a real child chart node with a non-empty `properties.Javascript` (a `ChartJsModel` with `js` +
  `replacements` bound to a query that returns rows). Charts are NOT offline-verifiable — you cannot confirm
  one renders, so `test-scenarios.md` must carry a scenario per chart saying what it should show
  (doc 21/22, Operating Principle 4).
- [BOTH] IMPORT PRECONDITION: the receiving project must be `type == REPORT`, or its rep-objects + DB are skipped on
  import. The `empty` export is REPORT-typed — base new work on it.
- [BOTH] DYNAMIC vs STATIC: you build the dynamic path (dynamic-cruds.json + a business schema in project-db.dump).
  The `erp` static path's COMPILED Java @Crud logic can't be reconstructed from an export alone — BUT if the
  schema + data are already in the dump (a "half-converted" export), you can wire dynamic CRUDs over them so the
  app runs with no Java service (Scenario B; doc/builder/erp/, doc 18).
- [BOTH] WHEN WIRING AN EXISTING SCHEMA (data already in the dump), honor the WHOLE schema, not just column names:
  * CHECK constraints (in schema.checkConstraints[], NOT the table ddl — see `db show <table>`): every status/enum
    LITERAL a create/update/lifecycle method writes must be in the allowed set, or it throws on the first real row.
  * NOT NULL / defaults / audit columns (creation_time/modification_time via now()) / single-company auto-fill;
    on update, COALESCE(:v, col) NOT NULL columns the form doesn't submit.
  * enum-lookup FK -> surface lookup.code (flat string); business FK -> nested `__` alias {ref:{id,code,name}};
    reference the executor's snake<->camel + `:x__id` path binding.
- [BOTH] ENUMERATE EVERY CRUD CONSUMER before claiming coverage: crud.table/crud.tree columns, form controls,
  dynaform.form.list.field SUB-GRID columns, choices rules, lifecycle action rules. A dotted `ref.code`/`ref.name`
  needs findAll (and the lines JSON) to surface that leaf, not just `{id}`.
- [BOTH] ENUM DROPDOWNS need a `settings.enumValues` snapshot (or a choices rule): after import the enum registry is
  empty and Class.forName(app enum) fails in a REPORT project, so a dataClass-only dropdown renders blank.
- [BOTH] CHOICES RULES (a dropdown/autocomplete `settings.ruleIdentifier`) MUST end by converting rows to option pairs —
  dropdown -> `return service.global.conversion.toSelectOptions(list,"<key>","<display>")` (use
  `toSelectOptionsLocalized` when the display field is `localized:true`, else labels stick to the base locale, e.g.
  always the base locale); autocomplete -> `toAutoCompleteOptions(list,"<display>")`. Returning a RAW `findAll`/`find`
  entity list -> the picker shows "No results found" AND the Show-Nav affordance vanishes (`validate` ERRORs on
  this via `_check_choices_rules`). For a SEARCHABLE dropdown (`searchEnabled`) use the platform pipeline per
  (crud, searchField X): SQL `acFindAllBy<Cap(X)>Like` (single typed `:X`, `defaultValue ''`) + Groovy wrapper
  `acFindBy<Cap(X)>Like` + rule `RIMM_FILT_<alias>_<X>`; NEVER a partial `findAll([<key>...])` (the default
  multi-optional findAll then throws Postgres "could not determine data type of parameter $1"). Recipe: 02 §4a.
- [BOTH] DOCUMENT (header+lines) delete MUST cascade to child lines (GROOVY deleteLines + header delete); a bare
  DELETE FROM header FK-fails on any doc with lines.
- [FILE] PDF templates ARE exported/imported in `.mrjun` (`rep-objects.pdfTemplates[]`, like mail templates in

- [BOTH] WORKFLOWS ARE NOT OPTIONAL when the PRD has a process. If the PRD describes a multi-step human process (intake →
